gPRC consist of several <strong>specifications</strong> initially created by Google (as "Stubby" to connect the large number of microservices running within and across its data centers), open-sourced in March 2015:

   * https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md prescribed the format a gRPC service must follow for consistentcy across platforms and implementations. So gRPC eliminates debate and saves developer time.
   * https://github.com/protocolbuffers/protobuf <a target="_blank" href="https://developers.google.com/protocol-buffers/docs/proto3">https://developers.google.com/protocol-buffers/docs/proto3</a> contracts
   * HTTP/2 transport for bi-directional initiation of binary exchanges

## Streaming bi-directional

"Remote Procedure Calls" and HTTP/2 are the mechanisms which enables gRPC programs to support <strong>bi-directional streaming</strong>, allowing gRPC services to push messages (without polling as with HTTP v1).

A gRPC service supports all streaming combinations:
   * unary (no streaming)
   * server to client streaming
   * client to server streaming 
   * bi-directional streaming
   <br /><br />

gRPC was designed to use HTTP/2 transport, a major revision of HTTP. The HTTP/2 protocol handles bi-directional streaming.

Microsoft's <a target="_blank" href="https://learn.microsoft.com/en-us/aspnet/core/signalr/introduction?view=aspnetcore-6.0">SignalR</a> provides a framework for persisten connections.


### Browser gRPC JSON Transcoding

Browsers common in 2022 (Google Chrome, Safari, Firefox, etc.) uses HTTP v1 protocol.

HTTP v1 traffic is designed (in 1999) to be <strong>one-way</strong> -- with interactions beginning from the client to the server.

To get around this, programmers had to use hacks such as "long-polling".

<a name="grpc-web"></a>

<strong>gRPC JSON transcoding</strong> allows browser apps to call gRPC services as if they were RESTful APIs with JSON. The browser app doesn't need to generate a gRPC client or know anything about gRPC. RESTful APIs can be automatically created from gRPC services by annotating the .proto file with HTTP metadata. Transcoding allows an app to support both gRPC and JSON web APIs without duplicating the effort of building separate services for both.

### .Proto contract file for code gen

A core file to gRPC development is the <strong>.proto file</strong>, which defines the contract of gRPC services and messages. 

From this file, gRPC frameworks <strong>generate</strong> a service base class, messages, and a complete client. All gRPC frameworks provide first-class support for code generation. 

Not having to write a client saves significant development time in applications with many services.

A unique design is that the same .proto file is shared between the server and client. Have both messages and client code generated from end to end eliminates duplication of messages on the client and server. 

### JSON human-readable, and slow

HTTP-based REST API exchanges JSON payloads, which is human-readable and browser-readable.

But that readability comes at a cost of a lot of bytes going through the wire, which means slow,
and uses up server resources.

Instead of JSON text, gRPC exchanges <strong>binary</strong> data with other programs using 
<a target="_blank" href="https://developers.google.com/protocol-buffers/docs/overview">Protocol Buffers (Protobuf)</a> as the interface description language and mechanism for <strong>serializing structured data</strong>.

Being binary, Protobuf payloads travel through the internet much quicker than JSON. 
That's important for streaming apps.

HTTP/2 is also fast because it grpeliminates <a target="_blank" href="https://www.wikiwand.com/en/Head-of-line_blocking">head-of-line blocking</a> by allowing multiplexing of multiple HTTP/2 calls over a single TCP connection. 


## Metadata

Instead of storing data to be exchanged in a HTTP request header, gRPC stores key-value data in "Metadata" that can be set from either the client or server side.

Clients can assign a Header.
Servers can assign Trailers as well.

## Interceptors

gRPC can intercept requests and responses, to manipulate each function call to add additional info such as logs to track response time, etc.

cancellation.

## Deadline timeouts

gRPC allows clients to specify how long they are willing to wait for an RPC to complete. A <a target="_blank" href="https://grpc.io/blog/deadlines">deadline</a> is sent to the server so that the server can "timeout" in-progress gRPC/HTTP/database requests.

gRPC also provides features such as authentication, bidirectional streaming and flow control, blocking or nonblocking bindings.
