## Component Tests 

Some of the demo apps are presented with a link to <a target="_blank" href="https://help.sap.com/saphelp_scm700_ehp03/helpdata/en/26/96ab50faad458f9b4027ec2f9b884d/frameset.htm">OPA5 (One Page Acceptance Tests)</a> for that app.

OPA5 is a JavaScript-based API for controlling SAPUI5 controls used by "component-level tests" as illustrated by <a target="_blank" href="https://www.linkedin.com/in/mikewcohn/">Mike Cohn</a>'s book "Succeeding with Agile" and described by <a target="_blank" href="https://blogs.sap.com/2018/10/03/testing-your-sapui5-application-with-opa5/">this blog</a>.

See <a target="_blank" href="https://openui5.hana.ondemand.com/#/topic/8615a0b9088645ae936dbb8bbce5d01d">Simulating User Interactions on Controls</a>


So it can be used with JavaScript unit test frameworks such as QUnit, Sinon, or Jasmine.



It hides asynchronicity using a polling mechanism to test user interactions, inner-app navigation, integration with SAPUI5, and data binding as well as navigation. 

OPA5's limitations include:

   * Screen capturing
   * Testing across more than one page
   * Remote test execution
   * End-to-end tests (due to authentication issues and fragility of test data)

## Why Flood.io Elements?

Traditional JMeter Java or LoadRunner C scripts were designed to mimic the exchange of <strong>static</strong> HTML between user client and web server. Such tools are able to pretend to be hundreds of actual users on a single server because it generates requests but does not do much with responses from web servers.

Apps today are still built for users who access internet browsers such a Google Chrome.

But modern apps are built using UI framework libraries such as Angular, React, Vue.
Such frameworks have JavaScript perform actions that operate within user client browser programs that <strong>dynamically</strong> alter the HTML and CSS processed by the browser.

Traditional scripts required custom coding to process ASP.NET apps which exchanged an "ACTIVE STATE" containing instructions on how forms are processed. Such complications can be avoided when crafting scripts that focus on browser JavaScript rather than interpreting HTML protocol.

## Scripting

Rather than maintaining several scripts, it is usually more productive on the long run to edit a single load testing script project. TODO: <strong>Feature flags</strong> are added in the script to control what each run exercises among different aspects of the infrastructure or app. Below is a typical sequence of concerns:

   1. "Website not available" page to stress the load balancer
   2. Just Landing page to stress the network infrastrure
   3. User registration and login to stress authentication infrastructure
   4. User menu navigation to stress web server infrastructure such as logging
   5. User browsing to stress random database access efficiency
   6. Report generation to stress sequential database access efficiency
   7. User data submission to stress queue overflow detection and state handling needed for scaling
   <br /><br />

A "workload model" defines the mix of the above to mimic load expected in actual production usage.

So that all requests can go to a different URL on a different environment with only a single change,
scripts are created using TODO: <strong>parameters</strong> that can be specified externally when invoking a run.

To replicate the additional activity within a browser, Flood.io Elements browser-level scripts are written in modern JavaScript or TypeScript, which generates JavaScript. Scipts containing Typescript have a file extention of ".ts", as in " test.ts".
