## One source file to rule them all

Pulumi's technologies enable developers to manage resources (Kubernetes, Serverless Lambdas/Functions, etc.) within <a href="#Clouds">multiple clouds</a> by coding in general programming languages 
referencing Pulumi's SDK libraries rather than editing declarative text files (in YAML of AWS Cloud Formation, <a target="_blank" href="https://wilsonmar.github.io/terraform">HCL of Terraform</a>).

As an example, here's JavaScript for Pulumi to create a new bucket in AWS S3:

   <pre>
   var aws = require("@pulumi/aws");
   const bucket = new aws.s3.Bucket("my-bucket");
   </pre>

   * When inside a .js file, "my-bucket" can be substituted with a <strong>variable</strong>.
   * The lines can be reused by being within a <strong>loop</strong> or placed in functions, and classes.
   * A single source code file can operate (transfer data) <strong>across several clouds</strong> (AWS, Azure, GCP, OpenStack, VMWare vSphere, etc.).
   * Use of general programming languages enable incorporation of code such as sending out emails, SMS texts, Slack notifications, etc.
   * Enforced error handling, compiler errors on invalid syntax, stack track debugging with line numbers.
   <br /><br />

The above is akin to calls to the AWS Boto3 Python library, but Pulumi provides more languages and for other cloud platforms and services in those clouds (such as Kubernetes and serverless lambdas/functions).

This is the same experience as <a target="_blank" href="https://github.com/kris-nova/me">Kris Nova</a> who <a target="_blank" href="https://about.sourcegraph.com/go/valuable-lessons-in-over-engineering-the-core-of-kubernetes-kops">on July 13, 2017 blogged</a> about transitioning from the YAML in kops cluster tool: "We replaced 1,000 lines of YAML with 10 Go structs and people started contributing again".

The sample code above is specific to a particular cloud platform (aws).

Languages supported are

   * go for GoLang (as in aws-go-s3-folder)
   * js for JavaScript
   * ts for TypeScript (a wrapper over JavaScript)
   * py for Python 3.6+ (https://pulumi.io/reference/python.html) https://pypi.org/project/pulumi/
   <br /><br />

Pulumi works kinda like Microsoft's <a target="_blank" href="https://github.com/dotnet/coreclr">.NET CLR</a> (Common Language Runtime) which compiles several languages into a common set of instructions at the machine level. In fact, Pulumi's engine was created by some of the people who worked on Microsoft's CLR
(Matt Ellis @ellismg, Pat Gavlin, etc.)

## Dependencies & State like Terraform

The Pulumi engine is written in GoLang<a target="_blank" href="https://www.youtube.com/watch?v=YMAe59BYzm4&t=21m0s">*</a>

Pulumi determines the sequence which infrastucture components need to be created by compiling programming code languages. Internally, Pulumi resolves dependencies by building a data stucture (a Directed Acyclic Graph like Git does) needed to build the desired state requested from programs.

Pulumi stores its own copy of the current <strong>state</strong> of each stack in transactional <strong>snapshots</strong> called <strong>checkpoints</strong> at various points in time. 
This works like Puppet which makes a "diff" of the goal state and compares it versus current state to identify drift or what needs to be updated.

This is similar to what Hashicorp's Terraform does under the covers.

* <a target="_blank" href="https://github.com/pulumi/terraform">https://github.com/pulumi/terraform</a> is an adaptation of<br /><a target="_blank" href="https://github.com/hashicorp/terraform">https://github.com/hashicorp/terraform</a>
<br /><br />

## \#NoYAML for True DevOps + SRE

Pulumi's approach solves a fundamental problem for DevSecOps.

PROTIP: Coding YAML to configure AWS CloudFormation or Terraform declarative DSL, with their thousands of cryptic settings, is a complexity which <strong>requires dedicated specialists</strong>.
Because they hard to find, such experts are relegated to work in a silo, separate from development people who have to literally get in line to talk to them.

Such separation does not satisfy the need for increasing delivery speed, namely:

> "Share ownership with developers by using the same tools and techniques across the stack"<a target="_blank" href="https://cloud.google.com/blog/products/gcp/sre-vs-devops-competing-standards-or-close-friends">*</a>

By making it trivial for developers and testers to spin up and tear down lots of stacks, Pulumi reduces the friction and thus enhances the speed to test out each Pull Request (individual feature) or entire tiers of technology.

https://noyaml.com/ from code at https://github.com/ghuntley/noyaml
* https://arp242.net/weblog/yaml_probably_not_so_great_after_all.html


* https://twitter.com/ellism/status/1008728148131733504 "What if you used the same language and tools you use to define your app to define your infrastructure?"

* https://www.pulumi.com/docs/intro/concepts/

PROTIP: The brevity of Pulumi's code makes it ideal for the next advancement in technical tutorials.

PROTIP: So you can get to work quicker (without a background in other tools),
I built a Bash script to automatically install all the pre-requisite utilities and files to enable
Pulumi's multi-cloud and multi-language capabilities. 

<tt><strong><a target="_blank" href="https://github.com/wilsonmar/DevSecOps/blob/master/Pulumi/pulumi-setup.sh">https://github.com/wilsonmar/DevSecOps/blob/master/Pulumi/pulumi-setup.sh</a></strong></tt>

The shell script above installs packages in this specific sequence: 
xcode-cli, homebrew, VSCode, git, Python3 > aws & azure-cli,  Node.js, Go,  Docker, Pulumi CLI.

Included in the bottom of the script is a sample use of a simple Pulumi deployment before cleaning up so charges do not linger.

The script is designed to be <strong>idempotent</strong> in that it can be rerun repeatedly.
For this reason, the script deletes what is left over from a previous run.
The script also has a flag which defaults to deleting what was created at the end of the script, so billing is minimized.

PROTIP: I recommend that you edit and add to the bottom of installation scripts I've provided.
It only takes a few seconds to run.
This ensure that you have the environment necessary in case of configuration changes and upgrades.
And if you run into issues, the install portion of the script outputs version numbers to inform debugging efforts.
