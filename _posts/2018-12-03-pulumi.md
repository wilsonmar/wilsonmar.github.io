## One source file to rule them all

Pulumi's technologies enable developers to manage resources (Kubernetes, Serverless Lambdas/Functions, etc.) within <a href="#Clouds">multiple clouds</a> by coding in general programming languages 
referencing Pulumi's SDK libraries rather than editing declarative text files (in YAML of AWS Cloud Formation, HCL of Terraform, etc.).

With Pulumi, you can combine infrastructure definitions and application code in the same program source file
using <a target="_blank" href="https://pulumi.io/reference/pkg/nodejs/@pulumi/cloud-aws/index.html#API">@pulumi/cloud-aws API</a>.

As an example, here's JavaScript to create a new bucket in AWS S3:

   <pre>
   var aws = require("@pulumi/aws");
   const bucket = new aws.s3.Bucket("my-bucket");
   </pre>

   * When inside a .js file, "my-bucket" can be substituted with a <strong>variable</strong>.
   * The lines can be reused by being within a <strong>loop</strong> or placed in functions, and classes.
   * A single source code file can operate (transfer data) <strong>across several clouds</strong> (AWS, Azure, GCP, OpenStack, VMWare vSphere, etc.).
   * Use of general programming languages enable incorporation of code such as sending out emails, SMS texts, Slack notifications, etc.
   <br /><br />

The above is akin to calls to the AWS Boto3 Python library, but Pulumi provides  more languages and for other clouds platforms and services in those clouds (such as Kubernetes).

The sample code above is specific to a particular cloud platform (aws).

## Languages

Languages supported are

   * go for GoLang (as in aws-go-s3-folder)
   * js for JavaScript
   * ts for TypeScript (a wrapper over JavaScript)
   * py for Python 3.6+ (https://pulumi.io/reference/python.html) https://pypi.org/project/pulumi/
   <br /><br />

Pulumi works like Microsoft's <a target="_blank" href="https://github.com/dotnet/coreclr">.NET CLR</a> (Common Language Runtime) which compiles several languages into a common set of instructions at the machine level. In fact, it was created by some of the people who worked on Microsoft's CLR
(Matt Ellis @ellismg, Pat Gavlin, etc.)

Similarly, Pulumi determines the sequence which infrastucture components need to be created by compiling programming code languages. Internally, Pulumi builds a data stucture (a Directed Acyclic Graph like Git does) of the desired state requested that is common to all languages.

Pulumi stores its own copy of the current <strong>state</strong> of each stackin transactional snapshots called <strong>checkpoints</strong> at various points in time. This works like Puppet which makes a "diff" of the goal state versus current state.

## \#NoYAML for True DevOps + SRE

Being able to Use general-purpose coding "democratizes" for developers their control of cloud deployment functionality.

Coding YAML to configure AWS CloudFormation or Terraform declarative DSL, with their thousands of lines containing cryptic settings
is a complexity requires dedicated specialists to work in a silo, separate from development. 

Such separation does not satisfy the need for increasing delivery speed, namely:

> "Share ownership with developers by using the same tools and techniques across the stack"<a target="_blank" href="https://cloud.google.com/blog/products/gcp/sre-vs-devops-competing-standards-or-close-friends">*</a>

By making it trivial to spin up and tear down lots of stacks, Pulumi enables each developer or tester to spin up (and tear down) fresh separate stacks to test out each Pull Request (individual features), or split tiers of a service into many stacks that are linked together.

https://noyaml.com/ from code at https://github.com/ghuntley/noyaml
* https://arp242.net/weblog/yaml_probably_not_so_great_after_all.html
* https://tinyurl.com/lessons-in-over-engineering "We replaced 1,000 lines of YAML with 10 structs and people started contributing again"
* https://twitter.com/ellism/status/1008728148131733504 "What if you used the same language and tools you use to define your app to define your infrastructure?"
