## Organizational Controls

It's a lot cheaper and easier to install systems for coordinated teamwork early on that to disrupt the entire organization later on to achieve more agility through teamwork. Here are some systems needed to achieve standardization company-wide at the highest level of maturity.

A. Train and certify all employees to use a common <strong>task tracking</strong> system responding to alerts (Vendor: Jira).

B. <strong>Escalate</strong> tasks which are not resolved in a timely way (Vendor: PagerDuty)

C. Train and certify all <strong>email</strong> holders to recognize <strong>phishing</strong> attacks (Vendor: Knowbe4).

D. Get customers and vendors to <strong>secure emails</strong> using SPF etc in DNS (Vendor: Virtru).

E. Use <strong>MFA</strong> (Multi-Factor Authentication) for all logins (vendor: Microsoft Entra ID P2).

F. Provide each employee with a <strong>password manager</strong> to make it convenient to generate strong passwords and autofill websites so password reuse is not necessary.

G. Provide each employee with a <strong>VPN</strong> (Virtual Private Network) to encrypt traffic between their device and the company network.

H. Train and certify each employee to manage action levels from <strong>trends in dashboards</strong> (Vendor: Grafana, Tableau, Qlik, etc.)

## SLSA

The SLSA defines <a target="_blank" href="https://slsa.dev/spec/v0.1/requirements">actions</a> to achieve their 4 levels of security controls for software artifacts.

Level 0 - <strong>Unsigned provenance</strong> provides no guarantees of <strong>resilence</strong> against tampering.

Level 1 - A <strong>Scripted/automated build process</strong> generates provenance (metadata about how an artifact was built, including the build process, top-level source, and dependencies). This does not protect against tampering, but offers a basic level of code source identification and can aid in vulnerability management.

Level 2 - <strong>Version control</strong> in a host and a hosted build service (such as GitHub) that generates <strong>authenticated provenance</strong>, such as the use of hashes in a DAG (Directed Ascyclic Graph). This gives software consumers confidence in the origin of the software. At this level, the provenance prevents tampering to the extent that the build service is trusted.

Level 3 - The source and build platforms guarantee the <strong>auditability</strong> of the source and the integrity of the provenance to provide much stronger protections against tampering than earlier levels by threats such as cross-build contamination.

Level 4 - Two-person <strong>review of changes</strong> for catching mistakes and deterring bad behavior, such as procedures defined in <a target="_blank" href="https://wilsonmar.github.io/contributing/">this CONTRIBUTING doc</a>. A <strong>hermetic, reproducible build process</strong> to guarantee that the SBOM dependencies is complete. Reproducible builds provide many auditability and reliability benefits. This gives the consumer a high degree of confidence that the software has not been tampered with.

A. To limit the submission of unauthorized changes into GitHub repositories, enforce practices defined <a target="_blank" href="https://wilsonmar.github.io/contributing/">in my example CONTRIBUTING article</a>:
   A1. all changes be submitted through <strong>pull requests</strong> (PRs) and<br />

   A2. PRs be reviewed and approved by at least one other person before being merged into the main branch.<br />

B. To limit compromise of GitHub accounts, enforce:
   B1. <strong> MFA</strong> (Multi-Factor Authentication) for all logins (vendor: Microsoft Entra ID P2).<br />

   B2. Limit posting of emails and other sensitive information in GitHub profiles, issues, PRs, etc.<br />
   
C. To limit build from modified source:
   C1. Assign <strong>least privilege</strong> permissions to limit each user account to the minimum permissions needed to do their job.<br />

   C2. Segment builds into zones so each team is focused on their own content. This limits lateral movement by attackers.<br />

D. To limit compromised dependencies:
   D1. Create a <strong>SBOM</strong> (Software Bill of Materials) of each open-source library package down the chain of references.(Vendor: Artifactory XRay).<br />

   D2. In each dependency in the SBOM, raise an alert if a CVE has been reported for the package. (Vendor: GithHub Dependabot, Snyk, Sonatype, WhiteSource, BlackDuck, Synopsys, Veracode, Checkmarx, Contrast Security, Fortify, Qualys, Rapid7, RiskSense, Tenable, Trustwave, WhiteHat Security, ZeroNorth, etc.)<br />

   D3. Scan the code of each package for vulnerabilities such as exfiltrating data externally. (Vendor: socket.dev)

E. To limit use of compromised dependencies:
   E1. After each install, create a hash of each static (executable) file, then generate them repeatedly on a schedule to see if they have been changed to a potentially hacked version. <strong>File integrity</strong> host-based IDPS (Intrusion Detection and Protection System) Vendor: <a target="_blank" href="https://www.ossec.net/">Atomic OSSEC</a>, Solarwinds, <a target="_blank" href="https://www.tripwire.com/state-of-security/ot-security-risks-challenges-and-securing-your-environment">Tripwire</a><br />

F. To limit upload of modified packages:
   F1. After uploading a file, recalculate a hash of the file and compare it to the hash of the same file before it was uploaded. Raise an alert if the hashes are different.<br />

G. To limit compromise package repositories:
   G1. Limit <strong>permission to backup</strong> media to separate accounts so they can't be deleted and encrypted for ransomware.<br />

   G2. <strong>Segment</strong> the network into zones, with a firewall between each zone, and only allow the minimum ports and protocols needed for each zone. This limits lateral movement by attackers.<br />

   G3. Perform regular <strong>data backups</strong> to cloud for enabling data recovery.

   G4. <strong>Verify recovery</strong> to prove the ability to recover from backups and reinstalls.

H. To limit use of compromised packages:
   H1. Reference packages from a <strong>private repository</strong> housing packages downloaded from the public (Vendor: Artifactory, Quay, Nexus, etc.)<br />

   H2. <strong>Reference packages based on its hash</strong> (Vendor: Artifactory, Quay, Nexus, etc.)<br />

   H3. Configure each device based on security recommendations in its <a target="_blank" href="https://www.cisecurity.org/cis-benchmarks/"><strong>CIS Benchmark</strong></a>.<br />

   H4. Verify that each device is running the <strong>latest version</strong> of patches of OS, utilities, apps.<br />

   H4. <strong>Automate installs</strong> of the latest version of every component (OS, utilities, apps) on laptops and servers in case of infection. This include drivers, firmware, TLS version, etc.<br />

   H5. Send <strong>alerts to SIEM</strong> (<a target="_blank" href="https://wilsonmar.github.io/siem/">Security Information and Event Management</strong> system) upon irregular logins, when a device is added to or removed from the network, when data streams are larger or smaller than normal, etc. (Vendor: Microsoft Defender, Prometheus Cloud)

   H6. Regularly schedule a fake test attack sent to each device, to ensure that <strong>alerts works</strong> in SIEM.

   H7. Detect <strong>anomalies in network</strong> traffic, such as a sudden increase in the number of connections to a server, or a sudden increase in the number of bytes sent to a server.



### API & OT (Operational Technology) Security

U. Configure every node with certificates for two-way encryption using <strong>mTLS</strong> (Mutual TLS) between every node for all network connections.

V. Have API servers <a target="_blank" href="https://portswigger.net/web-security/jwt#exploiting-flawed-jwt-signature-verification">verify</a> JWT (JSON Web Tokens) signatures to block attempts at user impersonation. Sign JWT tokens with a private key, then verify the signature with a public key.

W. Enforce a strict whitelist of permitted hosts for the jku header.

X. Always set an expiration date for any tokens issued.

Y. Avoid sending tokens in URL parameter string, which end up in logs.

Z. Include the aud (audience) claim (or similar) to specify the intended recipient of the token. This prevents it from being used on different websites.

AA. Enable the issuing server to revoke tokens (on logout, for example).

AB. Setup secure video surveillance of remote hardware devices to provide a history of accesses.

AC. Use API management servers to assign API tokens so that the number of API calls per minute can be tracked and limited.

AD. Setup SNMP pings with authentication 


Standards for ICS (Industrial Control Systems) are defined by NIST (National Institute of Standards and Technology) as ISA/IEC-62443 or ISA-99 in the US and IEC (International Electrotechnical Commission) in Europe.
