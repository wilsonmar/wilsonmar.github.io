## Why - Who Needs Load Balancing?

Server load balancing <strong>scales "horizontally" </strong> to accomodate higher volume work
by distributing (balancing) client requests among several servers.
This allows more servers (hosts) to be added to handle additional load.
</p><p>
	Even if a single server can handle current load, 
	it is still a good idea to design and test your system to use a load balancer to distribute load so that
	stay up - upgrading one server while another continues running.
</p><p>
	Having "fault resilience" means that an alternative server can take over when,
	inevitably, a server crashes or just needs maintenance work done.
</p><p>
	Having your applications on more than one machine allows operations personnel to work on
	one machine while the other is busy working.
	This is called ensuring uninterrupted continuous <strong> avialability </strong>
	of mission-critical applications.
</p><p>
	It's also a good idea to test your system for its ability to handle growth
	when it's still fresh on developer's minds, since
	load balancing and fail-over issues can be quite complex.

## The Trouble with Load Balancing 

	A load balancer may not evenly distribute load among machines in the cluster.
	This can happen for several reasons:
</p><p>
	<strong>Session stickiness</strong>. 
	Once the IP of a client gets assigned to a particular server (at Login),
	it stays with that server until the session ends. 
	This is the case with <a href="sap_perf.htm">SAP SAPGUI R/3 application performance tuning<img alt="another page on this site" src="http://merc.tv/img/icons/go.png" width="11" height="12" /></a>
</p><p>
		Since each session poses different levels of load,
		load balacers which allocate based on frequency of allocation (such as round-robin)
		may over-allocate sessions to a server which ended up with users and sessions who
		consume a higher-than-average amount of resources.

   Thus, monitor in real-time the load on each individual resource in a pool.

## Load Balancing in AWS

<a target="_blank" href="https://www.youtube.com/watch?v=HKh54BkaOK0">VIDEO</a>: 
https://aws.amazon.com/elasticloadbalancing/

Elastic Load Balancing offers four types of load balancers that all feature the high availability, automatic scaling, and robust security necessary to make your applications fault tolerant.

* Classic Load Balancer provides basic load balancing across multiple Amazon EC2 instances and operates at both the request level and the connection level. Classic Load Balancer is intended for applications that were built within a <strong>EC2-Classic network</strong>. Charges are in Load Balancer Capacity Units (LCU) used per hour plus $0.008 per GB of data processed (the only type to charge by network). More expensive to wean users off legacy.

* Application Load Balancer distributes HTTP and HTTPS traffic and provides advanced request routing targeted at microservices and containers. Application Load Balancer routes traffic to targets within Amazon VPC based on the content of the request. Charges are in Charges are in Application Load Balancer Capacity Units (ALCU) used per hour.

* Network Load Balancer distributes Transmission Control Protocol (TCP), User Datagram Protocol (UDP), and Transport Layer Security (TLS) traffic where extreme performance is required. Network Load Balancer routes traffic to targets within Amazon VPC and is capable of handling millions of requests per second while maintaining ultra-low latencies. Charges are in Network Load Balancer Capacity Units (NLCU) per hour.

* Gateway Load Balancer makes it easy to deploy, scale, and run <strong>fleets of third-party virtual networking appliances</strong> (such as F5) for security, network analytics, etc. Gateway Load Balancer is transparent to the source and destination of traffic. Charges are in Gateway Load Balancer Capacity Units (GLCU) per hour. Gateway Load Balancer uses Gateway Load Balancer Endpoint (GWLBE), a new type of VPC Endpoint powered by AWS PrivateLink technology that simplifies how applications can securely exchange traffic with GWLB across VPC boundaries. GWLBE is priced and billed separately.

## Approaches for High Server Availability 

There are several basic types of load balancing:
</p><p>	<ol type="A">
	<li> <strong> Round robin DNS (RRDNS) </strong> involves client <a href="1tcpaddr.htm">DNS</a>
	servers to resolve a URL to multiple ip addresses (and thus multiple machines).
</p><p>
	The problem with "round robin" is that it
	blindly hits each server regardless of its ability to accept work.
	This scheme requires every server to be homogeneous (nearly identical). 
</p><p>
	RRDNS is not recommended because it places load balancing outside the organization
	to authoritative DNS servers which caches DNS A entries.
	Changes to those entries can take a long time to propagate throughout the internet.
</p><p>
	<li> <strong> Network-based </strong> load balancers 
	offer more sophisticated allocation algorithms.
Network Load Balancing operates at the NIC driver level to detect the failure of a server
	and reassigns client computer traffic among the remaining servers. 
</p><p>
	<a href="#MSNLB">Microsoft's NLB service</a> can take up to eight seconds to redirect load.
	<img src="http://merc.tv/img/htm.gif">
	<a target="_blank" href="http://support.microsoft.com/kb/323431"
	title="Retrieved November 13, 2007">
	How To Set Up TCP/IP for Network Load Balancing in Windows Server 2003</a>
	notes that
<blockquote>
	TCP/IP must be the only network protocol present on the cluster adapter. You must not add any other protocols (for example, Internetwork Packet Exchange [IPX]) to this adapter.	
</blockquote>
</p><p>
	Because traffic enters the network, network load balancing cannot withstand
	moderate Dos (Denial of Service) attacks as well as
	large-capacity front-end network <a href="#Appliancez">appliances</a>
	which detect ad filter out malicious traffic before it gets to the server.
</p><p>
	<li> <strong> Dispatcher or proxy / switch</strong> based load balancers resolves
	requests from clients directed to a <strong> single virtual IP address (VIP) </strong>.
	The load balancer then uses a <a href="#LBAlgor">
	load balancing algorithm</a> to distribute work to real IP addresses.
</p><p>
	Such "server-based" load balancing is done either by an application running on a regular server or an
	<a href="#Appliancez">appliance</a>.
</p><p>
		<ul>
		<li> Using regular PC machines (on standard operating systems such as Windows or UNIX)
		has the advantage that it can be replaced (after configuration) with another machine
		that is <strong>familiar </strong>to the staff. 
		There is less hassle from dealing with another vendor.</li>
</p><p>
		<img src="http://merc.tv/img/tool.gif" width="16" height="16" alt="tool" />
		Vendors of such an approach include Resonate, Rainfinity, and Stonebeat.
</p><p>
		<li> Using <a href="#Appliancez">dedicated <strong>appliance </strong> hardware</a>
	has the advantage of <strong>speed</strong>, since they use
	specialized Application Specific Integrated Circuit (ASIC) chips.
	They "have internal-bandwidth backbones capable of handling a Gbps worth of traffic."[2,p31]
</p><p>
		<img src="http://merc.tv/img/tool.gif" width="16" height="16" alt="tool" />
		Vendors of such an approach include F5, and Radware.
</p><p>
	"Firewall load balancers tend to max out at around 70 to 80 Mbps"[2,p9,60] 
</p><p>
	<a href="http://www.f5.com/"> BigIP from f5</a> also compresses (for HTTP 1.1),
	encrypts SSL network traffic, and centralizes the SSL key store onto a single machine.
	</li>
		</ul>
</p><p>
	However, an individual central dispatcher can become a single point of failure. So:
</p><p>
		<ul> A <strong>hot spare </strong> is a machine that's configured as a mirror image of the machine 
	it replaces if that fails.  It's also called a <strong> passive </strong> node if it sits
	unused until it's need to support a failover.
</p><p>
	Both the active and standby load balancers occassionally send out heartbeat messages
	such as VRRP (Virtual Router Redundancy Protocol, RFC 2338) format
	UDP packets to <strong>multicast IP 225.0.0.2 port 1985</strong>.
	(in the range from 224.0.0.0 to 239.255.255.255).
</p><p>
	Cisco has its HSRP (Hot Standby Routing Protocol) and 
	Extreme Networks has its ESRP (Extreme Standby Router Protocol).
</p><p>
	This communication can occur over a serial cable between two machines.
</p><p>
	Multicast can span several subnets, but they must reach their final destination 
	after a network latency of no more than 200 to 300 milliseconds. 
</p><p>
	The passive node takes over (assumes "master" status) 
	when it does not hear the "I'm alive" heartbeat from the other machine.
</p><p>
	Because failover can cause a VIP to be the destination address at different
	devices at different times, a VIP can be called "floating".
</p><p>
	<strong> Failback </strong> occurs when the failed server comes back online and takes 
	load back from the failover node. This happens after a transfer of client state information.
</p><p>
	To avoid "bridging loops" when each load balancer thinks the other is inactive,
	the ISO Level 2 Spanning-Tree Protocol (STP) is used to 
	set a cost for each port.
	This provides a way to block multiple paths by opening only the lowest-cost port
	(the highest-priority port).
	However, "STP is almost never used since it can take 10 seconds or more to react.
	Typically, a proprietary variation of a hot-standby protocol is used."[2,p59]
		</ul>
</p><p>
	<img src="http://merc.tv/img/caution.gif" width="15" height="14" alt="Caution!" border="0" />
	Proxies forward both client requests to servers and server responses to clients,
	so unless they can handle as much throughput as all the machines in its subnet,
	it can easily become a throughput bottleneck.
	</ol>
</p><p>
	Note: 
	Although not necessary for production work, "Individual Pass-Though VIPs"
	are requested/defined so that for performance measurement and troubleshooting,
	individual servers can be reached through the load balancer.
	
</p></ul>

## Mechanisms 
<ol type="A"><p>
	There are several distinguishing features among load balancers.
</p><p>
<a name="NATing"></a>
	<li> <strong>"NAT-based" IP firewall</strong>.
</p><p>
	"Flat-based" IP typology means the VIP and real IPs are on the same subnet
	(usually behind a firewall).
	FTP and streaming applications use this typology along with <a href="#ReturnPathz">
	Return Path DSR</a>.
</p><p>
	Many load balancers also have firewall capabilities 
	(packet filtering, stateful inspection, intrusion detection, etc.)
</p><p>
	More advanced load balancers enable the VIP to be on a different (more private/secure) 
	subnet than IPs on servers receiving traffic.
	In this case, the load balancer acts as a <strong>gateway</strong> between the two LANs.
</p><p>
	This is achieved with NAT (Network Address Translation).
	<a target="_blank" href="http://ietf.org/rfc/rfc1631.txt?number=1631">
	(RFC 1631)</a> which enables real servers to hide themselves as 
	non-routed <a target="_blank" href="http://ietf.org/rfc/rfc1918.txt?number=1918">
	RFC 1918</a> addresses.
</p><p>
	But this only allows one pair of load balancer machines.
</p><p>
<a name="LBAlgor"></a>
	<li><strong> Load allocation algorithms </strong> 
	within daemons (or windows services), which dynamically:
</p><p>
		<ul>
		1) listens for a "heartbeat"; or
<br />	2) periodically sends ICMP ECHO_REQUEST to measure RTT (Round Trip Time) "pings"; or
<br />	3) detect the status of bandwidth usage or CPU utilization on each server; or
<br />	4) counts the number of <strong>connections active </strong>on each server.
		</ul>
<p><p>
	BEA Loogic 8.1 is <a target="_blank" href="http://edocs.bea.com/wls/docs81/cluster/load_balancing.html#1045512">
	server affinity</a> that reduces the number of RMI sockets.
</p><p>
	SAP R/3's login balancing (SMLG) clustering technology makes the decision of which
	server receives a user for login based on 
		the <strong> number of users </strong> currently logged in and 
		<strong> response time</strong>,
		(not how many work processes are used at any moment).
</p><p>
	Once a SAP user is logged on a particular app server, the
	<strong> user session is pinned </strong> to that server.
	Background jobs are also assigned to a server,
	but a new job might get assigned to another server.

</p><p></li>
<a name="FailOverz"></a>
	<li><strong> failover automatic repartioning </strong> of client traffic among the 
	remaining servers in the cluster so that users experience continuous 
	performance Quality of Service (QoS).
</p><p>
	Within the <a href="#WeblogicProxy">
	BEA WebLogic 8.1 HttpClusterServlet Plug-in</a>, sessions are attached to a particular server by the client's IP address.
	This means that a server must stay up until all sessions finish (which can take many minutes).
</p><p>
	A failover mechanism must have an awareness of the progress of all activities 
	so that client sessions can continue to complete if processing stops.
</p><p>
	IP Multicasts are sent by each WebLogic server to broadcast their status.
	Each Weblogic server listens for the one-to-many messages to update its own JNDI tree.
</p><p>
	Cisco's <strong>LoadDirector </strong> uses a "Cookie Sticky" feature that redirects traffic to the same physical machine
	by examining cookies.  
</p><p>
	"Virtualization" software (such as EMC VMware)
	automatically installs application software to meet demand.
</p><p>		</li>
	<li> <strong>Global load balancing</strong> that routes requests among several data centers
	over the WAN (Wide Area Network). "With cross-country latency at around 60 ms or more" [2,p10]
</p><p>		</li>
	<li> Intelligent response to denial of service flooding attacks.
</p><p>		</li>
<a name="ReturnPathz"></a>
	<li> <strong> Direct Server Return </strong> of traffic back to clients
</p><p>	
	The least sophisticated load balancers use "Route-path", where the load balancer acts as a 
	Layer 3 router. But this allows 3 or more load balancers.
</p><p>
	More sophisticated load balancers use "Bridge-path", where the load balancer acts as a 
	Layer 2 bridge between two LANs. However, this only works with flat-based nets.
</p><p>	
	Most sophisticated of all are when real servers (especially streaming and FTP servers) 
	can bypass going back to the Load Balancer and send responses directly to
	clients by using Direct Server Return (DSR).
	This is desirable because "web traffic has a ratio of about 1:8, which is one packet 
	out for every eight packets in."[2,p26]
</p><p>
	F5 calls this "nPath".
	Foundry calls it "SwitchBack".
</p><p>
	DSR works by configuring the IP alias on the server's loopback interface "lo"
	with the IP address of the VIP.
	This is done using the ifconfig command on Unix.
</p><p>
	The server needs to still bind to the real IP address as well so the load balancer can 
	perform health checks on the sever.
</p><p>
	The default route path of the server needs to point to the router rather than the load balancer.
</p><p>
	??? using MAC Address Translation (MAT) 
		</li>

</p><p>
	Like other load balancers, clients make requests using a single <strong>primary</strong> virtual IP address (VIP) for the cluster.
</p><p>
However, all incoming IP packets are received by the <strong>cluster adapter</strong> of each host
because NLB assigns listening cluster adapter on each host with the <strong>same MAC address</strong>
based on the VIP.
</p><p>
One of the hosts on the public subnet sends a MAC-layer (Layer 2) multicast to hosts 
on the local <strong>broadcast subnet</strong> of the cluster <strong>through another adapter</strong>.
These are received by a separate <strong>dedicated</strong> IP adapter on each host.
</p><p>
The NLB service <strong>runs on every host</strong> as an <strong>intermediate</strong> driver 
between the TCP/IP (HTTP & FTP) protocol and network adapter drivers 
within the <a href="1isotp.htm">Windows 2000 protocol stack</a>.
</p><p>
The service ignores unwanted packets and doesn't reroute packets to individual hosts.
</p><p>
Because potentially any host on the cluster can respond to a client,
a Web browser may receive various images within a single Web page from different hosts 
on a load-balanced cluster. 
</p><p>
The host that responds to a request is the host which know that it's the <strong>default host</strong>.
This is determined by the <strong>host priority number</strong> unique to every host.
That number is in the range of 1 to 32 because that's the NLB product's limit on hosts per cluster.
</p><p>
Each NLB server emits a <strong>heartbeat message</strong> to other hosts in the cluster, 
and listens for the heartbeat of other hosts. 
</p><p>
A host knows it's the default host if it doesn't hear another host with a
higher priority. This allows any host to be taken offline (for preventive maintenance, upgrading, etc.)
without disturbing cluster operations.
</p><p>
Each host responds to requests through its own unique <strong>dedicated</strong> IP address
so that other hosts know the source of the request.
</p><p>
Traffic arriving through a <strong>cluster adapter</strong> is redirected to the 
dedicated IP address of a specific host.
The dedicated IP address is always entered first on the list of IPs
so that outgoing connections from the cluster host are sourced with this IP address instead of a virtual IP address. 
</p><p>
The load-balancing server uses its algorithm to choose the best available server for the client. 
To allow session state to be maintained in host memory, NLB directs all TCP connections from one client IP address to the same cluster host.
This behavior is controlled by the client affinity parameter.
</p><p>
Changing <strong>load percentages</strong> allow hosts with higher capacity to receive a larger fraction of the total client load. 
NLB doesn't take advantage of Win2K's performance information for load balancing. 
</p><p>
MS-NLB doesn't support <strong>delayed binding</strong>. 
Each server provides failover for every other server, 
thus the software provides load-balancing redundancy in an active-and-active implementation. 
</p><p>
