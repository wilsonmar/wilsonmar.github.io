This is a deep yet succinct tour of Hashicorp's Terraform Enterprise (TFE), presented in light of its competitors in the market.

This is in addition to <a target="_blank" href="https://wilsonmar.github.io/terraform">my tutorial on Terraform</a>> which covers basic features of the Open-Source (free) edition of Terraform. 

Terraform Open-source runs "on-prem." or configured within your server in public clouds (AWS, Azure, GCP, etc.).

<a target="_blank" href="https://www.terraform.io/docs/enterprise/before-installing/reference-architecture/index.html">Terraform docs</a>

"Terraform Enterprise" is licensed (paid) software which can run either as SaaS in the "Terraform Cloud" and on-prem. As with other SaaS products, Hashicorp provide HA (High Availability) resilience "under the hood" without effort by users.

   * "Point and click" adoption of templates instead of hand-coding

   * Instead of users submitting to a manual ticketing queue (which breaks/slows agility), TFE auto-approves if <strong>policies</strong> are satisfied.


## PaC (Policy as Code) options

When each change in policy code triggers automated checks for compliance in CI/CD pipelines, it's like having a Security Engineer always review every change, which is too costly to achieve manually.

Moreover, each review generates an <strong>attestation</strong> (evidence) to show auditors compliance (that security policies are continually enforced).

When security policies are not just in a Word document but defined and automated like source code and versioned in GitHub, TFE treats <strong>Policy as Code</strong> (PaC).

Other PaC vendors include <a target="_blank" href="https://harness.io/blog/continuous-delivery/policy-as-code/">Harness</a> SaaS, which makes use of the <a target="_blank" href="https://github.com/open-policy-agent/opa#example-api-authorization">open-source Open Policy Agent (OPA)</a>. 
OPA is used by many other services: Kafka, Kubernets, <a target="_blank" href="https://jupiterone.com/features/security-policy-as-code/">JupiterOne</a>, etc.
OPA is used by <a target="_blank" href="https://github.com/fugue/regula-action">open-source Regula</a>, which runs GitHub Actions to alert about noncompliant IaC code. <a target="_blank" href="https://regula.dev/">Regula</a> handles several formats of IaC specification file formats:

   * Terraform HCL code
   * JSON-formatted Terraform plans
   * AWS CloudFormation JSON/YAML templates
   <br /><br />

To "shift-left" checking, verify locally on laptops before resources are deployed in the public cloud. <a target="_blank" href="https://github.com/iacsecurity/tool-compare">github.com/iacsecurity/tool-compare</a> 
lists all policy checks and which tool performs them:

   * OSS Python-based <a target="_blank" href="https://github.com/bridgecrewio/checkov">Checkov</a> by <a target="_blank" href="https://bridgecrew.io/">Bridgecrew.io</a> (acquired by Palo Alto Networks)

## Policy languages

The language to define policies needs to be a programming language with if/then/else using variables, loops referencing arrays, functions, etc.

<a target="_blank" href="https://medium.com/@mathurvarun98/how-to-write-great-rego-policies-dc6117679c9f">NOTE</a>: OPA makes use of its yaml-format <a target="_blank" href="https://www.openpolicyagent.org/docs/latest/policy-language/">"Rego language"</a> for defining policy rules. Rego extends the <a target="_blank" href="https://en.wikipedia.org/wiki/Datalog">Datalog query language</a>.

OPA was created by <a target="_blank" href="https://academy.styra.com/courses/opa-rego">Styra.com</a>, which provides support and training on OPA and the Rego language. The Python-esque Rego language has <a target="_blank" href="https://thenewstack.io/5-things-you-didnt-know-about-open-policy-agent/">comprehensions</a>

By contrast, TFE admins define policies in Terraform's HCL manifests to .sentinel files containing Terraform's <strong>proprietary</strong> policy language. For syntax highlighting and more efficient working with Terraform code, install the <a target="_blank" href="https://github.com/hashicorp/vscode-terraform">VSCode add-on</a> (<a target="_blank" href="https://www.hashicorp.com/blog/announcing-the-terraform-visual-studio-code-extension-v2-0-0">announced June 2020</a>) which leverages a Terraform Language Server (terraform-ls) running locally.

### Terraform Sentinel

TFE provides a <a target="_blank" href="https://docs.hashicorp.com/sentinel/intro"><strong>sentinel</strong> v2 command</a> to provide policy checks ("guardrails") to provisioning of infrastructure from a VCS (Version Control System such as GitHub) containing IaC (Infrastructure as Code).

![tfe-flow-934x245](https://user-images.githubusercontent.com/300046/129673459-7e9127d9-d603-42dc-ba2c-023c03bd22ae.png)

The sentinel command processes policy logic in *.sentinel files.

Since January 20, 2021, a <a target="_blank" href="https://github.com/hashicorp/terraform-guides/tree/master/governance/third-generation">"third-generation" policy file</a> in a HCL (rather than JSON) format 
<tt>sentinel.hcl</tt> file defines a policy "manifest" file. 

HCL (Hashicorp Configuration Language) enables addition of comments in JSON files, which by definition does not recognize comments.

Example of HCL Sentinel manifest file:

   <pre>policy "restrict-allowed-vm-types" {
    enforcement_level = "soft-mandatory"
}
policy "restrict-app-service-to-https" {
    enforcement_level = "advisory"
}
policy "enforce-mandatory-tags" {
    enforcement_level = "hard-mandatory"
}
   </pre>

Each policy has an <strong>enforcement_level</strong>.

The above sample code is from <a target="_blank" href="https://github.com/stoffee/tfe-workshop-sentinel/blob/master/enforce-mandatory-tags.sentinel">here</a>.

<a target="_blank" href="https://www.terraform.io/docs/cloud/sentinel/examples.html">Example TFE policies</a> in <a target="_blank" href="https://github.com/hashicorp/tfe-policies-example">Hashicorp's GitHub</a> include cost and policy sub-commands.

## TFE Architecture

<a target="_blank" href="https://www.terraform.io/docs/enterprise/system-overview/reliability-availability.html">This data flow diagram</a> shows TFE's internal technology choices:

![tfe-data-flow-2400x1288](https://user-images.githubusercontent.com/300046/128644885-d5c0e735-b00b-4a23-91e6-23dda96bc0bb.png)

Application Layer:

   * TFE Core - A Rails application at the center of Terraform Enterprise; consists of web frontends and background workers

   * TFE Services - A set of Go services that provide various pieces of key functionality for Terraform Enterprise

   * Terraform Workers - A fleet of isolated execution environments that perform Terraform Runs on behalf of Terraform Enterprise users

Coordination Layer:

   * Redis - Used for Rails caching and coordination between TFE Core's web and background workers

   * RabbitMQ Used for Terraform Worker job coordination

Storage Layer:

   * PostgreSQL Database - Serves as the primary store of Terraform Enterprise's application data such as workspace settings and user settings

   * Blob Storage - Used for storage of Terraform state files, plan files, configuration, and output logs

   * HashiCorp Vault - Used for encryption of sensitive data. There are two types of Vault data in Terraform Enterprise - key material and storage backend data.

   * Configuration Data - The information provided and/or generated at install-time (e.g. database credentials, hostname, etc.)

## Sentinel coding

The types of Sentinel policies, correspond to the three Sentinel imports: 

   * <a target="_blank" href="https://www.terraform.io/docs/enterprise/sentinel/import/tfplan.html">tfplan</a> - to restrict attributes of specific resources or data sources.

   * tfconfig - to restrict the configuration of Terraform modules, variables, resources, data sources, providers, provisioners, and outputs.

   * tfstate - to check whether previously provisioned resources, data sources, or outputs have attribute values that are no longer allowed by governance policies. 

   * other imports to allow Sentinel policies to inspect workspace metadata attributes and cost estimates.

### TFE-CLI

https://github.com/rgreinho/tfe-cli

The tfh program in https://github.com/hashicorp-community/tf-helper
provides commands for performing operations relating to HashiCorp Terraform. The operations include interacting with Terraform Enterprise (TFE) and also reporting on and manipulating other Terraform artifacts. The scripts are not necessary to use Terraform Enterprise's core workflows, but they offer a convenient interface for manual actions on the command line.

Its tfh pushconfig and tfh pushvars commands replace and extend the functionality of the deprecated terraform push command. Use it to upload configurations, start runs, and change and retrieve variables using the new Terraform Enterprise API at https://www.terraform.io/docs/enterprise/api/index.html

## Ensure follow-up with ServiceNow

AWS offers the <a target="_blank" href="https://aws.amazon.com/security-hub/">AWS Security Hub service</a> which publishes security alerts from other services across regions. 

AWS Security Hub presents security alerts as a web page for users to manually review.

The cumbersome aspect here is that a central SOC team must individually analyze each alert, then notify the appropriate individuals to request remediation action. 

AWS Security Hub also sends emails of crucial and high alerts to designated individuals, but emails often are not read.

So companies that have ServiceNow make use of the <a target="_blank" href="https://aws.amazon.com/about-aws/whats-new/2020/12/aws-security-hub-now-supports-bidirectional-integration-with-service-now-itsm/">two-way automatic integration between ServiceNow and AWS Security Hub</a>

More: https://aws.amazon.com/blogs/mt/tag/servicenow/
