This tutorial describes the different options to <a name="Install">install</a>, <a href="#Uninstall">uninstall</a>, configure, and use various versions of Python with its various packages, all running in a virtual environment also managed by pyenv.

## Why pipenv?

pipenv brings <a target="_blank" href="https://pipenv.pypa.io/en/latest/">"the best of all packaging worlds (bundler, composer, npm, cargo, yarn, etc.) to the Python world."</a>

The value of pyenv is:

   * Install Python in your user space (without need for sudo)
   * Install multiple parallel versions of Python
   * Dynamically specify the exact Python version you want
   * Switch between installed versions without resetting your bash session
   <br /><br />

## What is the magic of pyenv?

In this article I take a carefully crafted narrated tour. Here is a <strong>hands-on "deep dive"</strong> tutorial so you better grasp the complexities in a shorter time. Why? Because I haven't seen one on the internet. 

   pyenv uses a technique called <strong>"rehashing"</strong> so it can switch among multiple versions of Python2 or Python3.
   
   Commands for the operating system to execute "python3" are <strong>intercepted</strong> by a <strong>shim</strong> executable which passes commands along to the actual Python installation of the desired version.

   <a href="#PATH-edit">That's achieved</a> by a line at the bottom of your ~/.bash_profile which makes the operating system search in the shims folder for programs:

   <pre>export PATH="$PYENV_ROOT/shims:$PATH"</pre>

This technique is possible because the operating system searches for executables in folders in the PATH from left to right.

Thus, <tt>which aws</tt> would return:

   <pre>/Users/wilson_mar/.pyenv/shims/aws</pre>



## Competitors

The alternative to Pyenv is <strong>Conda</strong> and <strong>MiniConda</strong>.

## What are installed?

   PROTIP: Before installing things, first see what is already installed.

   </strong></pre>

   Different installers install Python in different paths (but instead of "wilson_mar", you'll see your own user name):

   <pre>python is /Users/wilson_mar/.pyenv/shims/python

   </pre>

   You are good to go with Pipenv if you see in the first response to the <a href="#TypeInstalled">type -a python</a> command (but instead of "wilson_mar", you'll see your own user name):

   <pre>python3 is /Users/wilson_mar/.pyenv/shims/python3
   </pre>

   PROTIP: There may be several Python executables installed in different folders. But the Python program actually executed is the <strong>first one</strong> that the operating system finds among folders defined in <a href="#PATH-edit">your PATH</a> system variable defined in <tt>~/.bash_profile</tt> or ~/.zshenv. The operating system searches for executables in each folder in the PATH, from left to right.

   <a name="InstallPython3"></a>

   ## Ways to Install Python3

   Before pyenv, people define what version of "python" is executed by editing the PATH variable -- putting the path to Python3 executables before Python2 in $PATH. To have Python3 execute instead of Python2:

   <pre>export PATH="/usr/local/python3:$PATH"</pre>

   (Colon characters separate folders in the PATH)

   Alternately, Azure recommends this line at the bottom of <tt>~/.bash_profile</tt> files:

   <pre>export PATH="/usr/local/opt/python@3.8/bin:$PATH"</pre>

   The line above overrides the system's <a href="#TypeInstalled">type command described above</a>.


   ### Don't alias with pyenv

   Some add aliases within the <tt>~/.bash_profile</tt> or <tt>~/.zshenv</tt> file:

   <pre>alias python=python3
   alias pip=pip3</pre>

   But don't do that when you're using pyenv, which makes use of shims.

   <a name="PATH-edit"></a>

   ## How is Pyenv enabled?

1. Edit your <tt>~/.bash_profile</tt> and/or ~/.zshenv file so that the PATH comes before "/usr/local/bin" and "/usr/bin" where others install programs:

   <pre># Set it so ~/.pyenv provides Python before others of the same name:
export PYENV_ROOT=$(pyenv root)
export PATH="$PYENV_ROOT/shims:$PATH"
   </pre>

   Put the above at the <strong>bottom</strong> of the file.

   Alternately, if you don't want to mess with a text editor, use this command:

   <pre>echo 'export PATH="$(pyenv root)/bin:$PATH"' >> ~/.bash_profile
   </pre>

   Instead of .bash_profile, specify ~/.zshrc or ~/.bashrc (for Ubuntu/Fedora).

   <pre>$(pyenv root)/shims:/usr/local/bin:/usr/bin:/bin
   </pre>

   (Colon characters separate folders in the PATH)

1. Whether you edited your shell script or not, restart your shell terminal so the path changes take effect:

   <pre><strong>exec "$SHELL"
   source ~/.bash_profile</strong></pre>
   or 

   <pre><strong>~/.zshrc</strong></pre>
   
1. Verify:

   <pre>echo "$PATH" >path.txt
   edit path.txt
   rm path.txt
   </pre>

1. Confirm whether pyenv is now active:

   <pre><strong>which python</strong></pre>

   Response should be:

   <pre>/Users/wilson_mar/.pyenv/shims/python</pre>
   
   ("wilson_mar" would be replaced with your user name)

   ## Order of Path override

   When a shim (such as "python") is executed, it calls pyenv which determines which Python release to use by reading sources in this order:

   1. $PYENV_VERSION environment variable
   2. pyenv local x.y.z
   3. pyenv global x.y.z
   <br /><br />

   This means the <tt>PYENV_VERSION</tt> environment variable overrides all other specifications. 
   
1. Set this environment variable in your current shell session using the pyenv shell command.

   If the PYENV_VERSION system variable is not specified, the application-specific <tt>.python-version</tt> file in the <strong>current directory</strong>. 
   
1. Modify the current directory's .python-version file with the command:

   <pre><strong>pyenv local 2.7.15</strong></pre>

   If there is no <tt>.python-version</tt> file locally, parent directories are searched upward until reaching the root of your filesystem.

   If no .python-version is specified in any folder, the global $(pyenv root)/version file. 
   
1. Modify the global file using the command:

   <pre><strong>pyenv global 3.7.7</strong></pre>
   
   If the global version file is not present, pyenv assumes you want to use the "system" Python. (In other words, whatever version would run if pyenv weren't in your PATH.)

## Virtual Environments #

Both Pipenv and Pipenv automatically creates and manages a virtualenv for your projects. But only Pipenv adds/removes packages from your Pipfile as you install/uninstall packages. Pipenv generates the Pipfile.lock file used to produce deterministic builds.

Pipenv enables always use the latest versions of dependencies, to minimize security risks arising from outdated components.

   pyenv copies an entire Python installation every time a new pyenv version is created.

   By contrast, virtualenv makes use of symbolic links, which decreases the size of each virtualenv. 

   There are two utilities to add virtualenv functionality to pyenv: 
   <a target="_blank" href="https://github.com/pyenv/pyenv-virtualenvwrapper">pyenv-virtualenvwrapper</a>

   ### Setup Virtual environments

   There are several ways to enter and setup a virtual environment:

1. Navigate to where you .py files are. This is important.

1. Set up a virtual environment in the present working directory, using a common conventional name:

   <pre><strong>python -m venv venv</strong></pre>

   No response is returned if it's all good.
   
   The above creates a virtual folder named after the project.

   To deactivate, type:

   <pre><strong>exit</strong></pre>

   Alternately, to activate virtualenv, run:
   
   <pre><strong>pipenv shell</strong></pre>

   Alternatively, run a command inside the virtualenv 
   
   <pre><strong>pipenv run
   </strong></pre>

1. Activate the virtual environment in the present working directory:

   <pre><strong>source ./venv/bin/activate</strong></pre>

   This would turn the command prompt as a constant reminder:

   <tt>(venv)</tt>
   
1. which python

   <pre>/Users/... my_project/venv/bin/python</pre>


   ## Pipfile.lock

   The <tt>Pipfile.lock</tt> file contains a hash of each package installed,
   which provides security. 
   The file pins semantic versions of all dependencies and sub-dependencies, which provides replicable environments.
