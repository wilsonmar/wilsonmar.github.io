The Open Policy Agent (OPA, pronounced "oh-pa"), is an open-source, general-purpose (central) "engine" that
makes policy decisions (separately from policy enforcement).

OPA is used within 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/terraform">Terraform</a> Enterprise Cloud,
Scalr Policy Enforcement for Terraform,
Stackforge.com,
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/kubernetes-introduction">Kubernetes</a> Authorization, Provisioning, and Admission Control, 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/envoy-introduction">Envoy</a>,
app microservices, 
CI/CD pipelines (Jenkins Job Trigger Policy Enforcement), 
API gateways (Flask OPA), 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/ecosystem/#google-calendar-detail">Google Calendar</a>,
AWS CloudFormation Hook,
and elsewhere.

OPA reads and processes <strong>Rego</strong> high-level declarative language code which defines policy decisions and outputs.

OPA can run <a target="_blank" href="https://www.openpolicyagent.org/docs/latest/#5-try-opa-as-a-go-library">within Go programs</a>.

When applications software needs to make a policy decision, it sends a REST API query to OPA with structured data (e.g., JSON) as input. Rego was purpose-built for expressing policies over complex hierarchical data structures. 

Examples of decisions:

   * Which users can access which resources.
   * Which times of day the system can be accessed at.

   * Which subnets egress traffic is allowed to.
   * Which clusters a workload must be deployed to.
   * Which registries binaries can be downloaded from.
   * Which OS capabilities a container can execute with.
   <br /><br />

In addition to simple yes/no or allow/deny answers, policies can generate arbitrary structured data as output.

   </pre>


## Sample Rego

This <a target="_blank" href="https://github.com/StyraInc/rego-style-guide#use-metadata-annotations">example</a> 
Rego file presents a standard for metadata:

<pre># METADATA
# title: Example
# description: Example package with documentation
package example

import future.keywords.contains
import future.keywords.if

# METADATA
# title: Deny non admin users
# description: Only admin users are allowed to access these resources
# related_resources:
# - https://docs.example.com/policy/rule/E123
# custom:
#   code: 401
#   error_id: E123  
deny contains {
	"code": metadata.custom.code,
	"message": sprintf("Unauthorized due to policy rule (%s, %s)", [
		metadata.custom.error_id,
		concat(",", [ref | ref := metadata.related_resources[_].ref]),
	]),
} if {
	input.admin == false

	metadata := rego.metadata.rule()
}
</pre>

The vertical bar | breaks a line in Rego (like \ breaks a line in Bash script).

Rego has more than <a target="_blank" href="https://www.openpolicyagent.org/docs/latest/policy-reference/#built-in-functions">
150 built-in functions</a> to compare, numbers (round), aggregates (count, min, max), arrays, sets, objects, strings, regex, glob, conversions, types (is_number), encoding, (jwt) token signing & verification, PEM certs, crypto, time, graphs, GraphQL, HTTP, AWS Request Signing, Azure net (CIDR), Debugging, Tracing.

https://www.openpolicyagent.org/docs/latest/policy-reference/#grammar

https://www.openpolicyagent.org/docs/latest/aws-cloudformation-hooks/

## Server Mode

Most uses of OPA is as a service responding to API calls.

1. To run the opa executable in server mode, configured to  use any decision as the default decision:

   <pre><strong>opa --server service1.rego \
   --set=default_decision=example/allow
   </strong></pre>

2. View process

   <pre><strong>ps -al | grep opa
   </strong></pre>

3. Pretend to be an application program:

   <pre>curl localhost:8181 -i -d @input.json -H 'Content-Type: application/json'
   </pre>
