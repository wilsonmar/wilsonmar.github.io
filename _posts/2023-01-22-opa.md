The Open Policy Agent (OPA, pronounced "oh-pa"), is an open-source, general-purpose (central) "engine" that
makes policy decisions (separately from policy enforcement).

The cartoon at <a target="_blank" href="https://www.openpolicyagent.org/">https://www.openpolicyagent.org</a>
shows the expansiveness of OPA and Rego.

OPA is used within 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/terraform">Terraform</a> Enterprise Cloud,
Scalr Policy Enforcement for Terraform,
Stackforge.com,
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/kubernetes-introduction">Kubernetes</a> Authorization, Provisioning, and Admission Control, 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/envoy-introduction">Envoy</a>,
app microservices, 
CI/CD pipelines (Jenkins Job Trigger Policy Enforcement), 
API gateways (Flask OPA), 
<a target="_blank" href="https://www.openpolicyagent.org/docs/latest/ecosystem/#google-calendar-detail">Google Calendar</a>,
AWS CloudFormation Hook,
and elsewhere.

OPA reads and processes policies written in a high-level declarative language called <strong>Rego</strong> (pronounced "ray-go").

OPA can run <a target="_blank" href="https://www.openpolicyagent.org/docs/latest/#5-try-opa-as-a-go-library">within Go programs</a>.

When applications software needs to make a policy decision, it sends a REST API query to OPA with structured data (e.g., JSON) as input. Rego was purpose-built for expressing policies over complex hierarchical data structures. 

Examples of decisions:

   * Which users can access which resources.
   * Which times of day the system can be accessed at.

   * Which subnets egress traffic is allowed to.
   * Which clusters a workload must be deployed to.
   * Which registries binaries can be downloaded from.
   * Which OS capabilities a container can execute with.
   <br /><br />

## Playground

1.  In an internet browser (Chrome), go to Sytra's Rego Playground default "hello world" Rego policy file:

    <a target="_blank" href="https://play.openpolicyagent.org/">https://play.openpolicyagent.org</a>

    It is the simplest example, which simply outputs static text within the code to a JSON file.

2.  Each <strong>keyword</strong> is like a program, and needs to be imported. Rego has more than <a target="_blank" href="https://www.openpolicyagent.org/docs/latest/policy-reference/#built-in-functions">150 built-in functions</a> to compare, numbers (round), aggregates (count, min, max), arrays, sets, objects, strings, regex, glob, conversions, types (is_number), encoding, (jwt) token signing & verification, PEM certs, crypto, time, graphs, GraphQL, HTTP, AWS Request Signing, Azure net (CIDR), Debugging, Tracing, etc.

3.  Click the blue "Evaluate" button to see OUTPUT generated.

    <pre>{
    "hello": true
    }
    </pre>

    "hello" is the key (variable) and "true" is the value.
    true/false values are called <strong>binary</strong> data types. 
    
    But policies can also output other data types: arbitrary data structures such as lists.

    Rego is called a <strong>declarative</strong> language so that policy authors can focus on what queries should <strong>return</strong> rather than how queries should be executed.
    
    "If then else" programmatic logic are carried out by keywords such as "if" are <strong>imported</strong> by statements such as:

    <pre>import future.keywords.if</pre>

    That "if" keyword can then be invoked in Rego statements such as:

    <pre>hello if input.message == "world"</pre>

    Varible key "message" is an attribute of "input", which is a global variable bound to the data sent to OPA by Kubernetes. 

    In Rego, the dot "." operator selects keys from objects.

4.  To make it real, change </tt>hello</tt> to <tt>doit</tt> on lines 23 and 25, then press "Evaluate" again.
   
    The main objective of Rego programming is to create OUTPUT JSON which define whether the reader of OUTPUT should:
    
    a). perform an action such as "doit", or<br />
    b). realize the value of some condition.

    PROTIP: For each error message, create a web page to show how to fix the error.

    ### Most used policy

    PROTIP: Checking for a valid tag is often the first policy to be added to control cloud usage in resources in a shared environment (cloud by a team using Terraform).

5.  Click "Examples" at the top for a list of other starter samples.
6.  Click "Kubernetes", then <a target="_blank" href="https://play.openpolicyagent.org/p/0FjgydMuVo">Label Existence</a>.
7.  Click "Evaluate" to get output:

    <pre>    "deny": [
        "Every resource must have a costcenter label"
    ]
    </pre>

    The Rego policy expects a valid value for cost center when it executes this:

    <pre>value := input.request.object.metadata.labels.costcenter
    </pre>

    PROTIP: Provide to workers example standard coding of the above hierarchy in their Kubernetes yaml so that Rego validation code can find them.

    <pre>"kind": "AdmissionReview",
    "request": {
        "kind": {
            "kind": "Pod",
            "version": "v1"
        },
        "object": {
            "metadata": {
                "name": "myapp",
                "labels": {
                    "costcenter": "cccode-12345"
                }
            },
     ...
    </pre>

    REMEMBER: When adding an item to the end of a list (such as after the metadata.name), make sure a comma is added.

8.  Click "Kubernetes", then <a target="_blank" href="https://play.openpolicyagent.org/p/0FjgydMuVo">Label Existence</a>. 

    To enable multiple policies to deny, the example makes use of <strong>double negative</strong> logic:

    <pre>deny contains msg if {
        not input.request.object.metadata.labels.costcenter
        msg := "Every resource must have a costcenter label"
    }
    </pre>

    <a target="_blank" href="https://www.fugue.co/blog/5-tips-for-using-the-rego-language-for-open-policy-agent-opa">
    A blog at Fugue</a> suggests use of <a target="_blank" href="https://brilliant.org/wiki/de-morgans-laws/">Augustus De Morgan’s laws</a> (Set Theory) to write policies using the negation of a compound statement.
    In this silly example:

    <pre>cannot_cut_pizza {
     input.people[_].profession != "mathematician"
    }
    </pre>

    That sets up use of a <strong>double negative</strong> 
    to make a policy that's easier to write and understand:

    <pre>default allow = false
    allow {
      not cannot_cut_pizza
    }
    </pre>

    For a better understanding, use <a target="_blank" href="https://courses.lumenlearning.com/waymakermath4libarts/chapter/demorgans-laws/">truth table</a> of granular values.

    ### Evaulation of Conditionls 

9.  <a target="_blank" href="https://play.openpolicyagent.org/p/0FjgydMuVo">This example</a> ensures that,  when PUT methods are used, the user and owner are the same when value "pets" is <strong>somewhere</strong> within the path:

    <pre>allow if {
	input.method == "PUT"
	some petid
	input.path = ["pets", petid]
	input.user == input.owner
    }
    </pre>

    All the "==" must resolve to true for allow to be true.

    ### Reserved words

    REMEMBER: Being declarative means <tt>some petid</tt> is specified before <br />
	<tt>input.path = ["pets", petid]</tt>

    <tt>some</tt> is one of the Rego language's <a target="_blank" href="">reserved words</a> which cannot be defined as a variable or function:

    * as
    * default
    * else
    * true, false
    * import
    * package
    * not
    * null
    * <strong>some</strong>
    * with
    <br /><br />

10. Achieve <tt>"allow": true</tt> by changing one email to be the same as the other email:

    <pre>{
    "method": "PUT",
    "owner": "bob@hooli.com",
    "path": [
        "pets",
        "pet113-987"
    ],
    "user": "bob@hooli.com"
    }
    </pre>

    BTW, In Real Life, emails would not be hard-coded.

In Rego, the vertical bar | continues a line (like \ breaks a line in Bash script).

## Sample Rego with metadata

This <a target="_blank" href="https://github.com/StyraInc/rego-style-guide#use-metadata-annotations">example</a> 
Rego file presents a standard for metadata:

<pre># METADATA
# title: Example
# description: Example package with documentation
package example

import future.keywords.contains
import future.keywords.if

# METADATA
# title: Deny non admin users
# description: Only admin users are allowed to access these resources
# related_resources:
# - https://docs.example.com/policy/rule/E123
# custom:
#   code: 401
#   error_id: E123  
deny contains {
	"code": metadata.custom.code,
	"message": sprintf("Unauthorized due to policy rule (%s, %s)", [
		metadata.custom.error_id,
		concat(",", [ref | ref := metadata.related_resources[_].ref]),
	]),
} if {
	input.admin == false

	metadata := rego.metadata.rule()
}
</pre>

## Start OPA Server Mode

opa can run in interactive mode, but 
most use OPA as a service listening for API calls.

1. To run the opa executable in server mode, configured to  use any decision as the default decision:

   <pre><strong>opa --server --set=default_decision=example/allow
   </strong></pre>

   Alternately, to process a single Rego file and exit:

   <pre><strong>opa --server --set=default_decision=example/allow \
   service1.rego
   </strong></pre>

   REMEMBER: By default OPA listens for HTTP connections on 0.0.0.0:8181

2.  View process

    <pre><strong>ps -al | grep opa
    </strong></pre>

3.  Push data file to the server:

    <pre><strong>curl -X PUT http://localhost:8181/v1/data/{myData} --data-binary @{myData}.json
    </strong></pre>

4.  Push rego file to the server

   <pre><strong>curl -X PUT http://localhost:8181/v1/policies/{mypolicy} --data-binary @{mypolicy}.rego
    </strong></pre>

5. Execute the rules

    <pre><strong>curl --location --request POST 'http://localhost:8181/v1/data/$policyPath$/{ruleName}' \
    --header 'Content-Type: text/plain' \
    --data-raw '{Input_Json}'
    </strong></pre>

6. Pretend to be an application program:

   <pre>curl localhost:8181 -i -d @input.json -H 'Content-Type: application/json'
   </pre>
