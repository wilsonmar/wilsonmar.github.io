With "Go" in the name one would think that it's written in the <a target="_blank" href="https://wilsonmar.github.io/golang/">Go language</a>.
But GoCD is actually built using Java and JRuby on Rails. It was re-branded in 2010 before Google released the Go language. 

GoCD's was as open-source in 2014 at <a target="_blank" href="https://github.com/gocd/gocd">https://github.com/gocd/gocd</a>. <a target="_blank" href="https://www.gocd.org/releases/#14-1-0">GoCD's releases</a> are <a target="_blank" href="https://semver.org/">sematically</a> tagged beginning with a year (19 for 2019). 

GoCD is from <a target="_blank" href="https://www.thoughtworks.com/">ThoughtWorks</a>, which makes money by providing <a target="_blank" href="https://www.gocd.org/plugins/">commercial (paid)</a> <a href="#Plugins">plugins for GoCD</a>, but primarily from consulting services. The company has a <a target="_blank" href="https://www.glassdoor.com/Reviews/ThoughtWorks-Reviews-E38334.htm">90% employee referral rating on Glassdoor.com</a>. It publishes future-thinking <a target="_blank" href="https://www.thoughtworks.com/radar">Tech Radar</a> each year and hosts <a target="_blank" href="https://www.youtube.com/playlist?list=PL8f-F_Zx8XA8JtEr7bIP4rQ7z3EWpc2Ss">XConf</a> in various cities.

<a target="_blank" href="https://martinfowler.com/">Martin Fowler</a>, Thoughtworks Chief Scientist since 2000 <a href="#[4]">[4]</a> (along with Jim Highsmith and other software visionaries) authored the <a target="_blank" href="https://agilemanifesto.org/">Agile Manifesto</a> in 2001.

Thoughtworkers Jez Humble, Chris Read, and Dan North presented their ground-breaking "Deployment Production Line" at the Agile conference in 2006.
While working on the oft-quoted 2010 book <a target="_blank" href="https://www.amazon.com/Continuous-Delivery-Deployment-Automation-Addison-Wesley-ebook/dp/B003YMNVC0">Continuous Delivery</a> with and David Farley, Jez Humble

## CI/CD Delivery to Production, not just Deploy to Test

The "CD" in GoCD is for "Continuous Delivery" (not just Deployment). As Humble states in his website <a target="_blank" href="https://continuousdelivery.com/">ContinuousDelivery.com</a>:

> "Continuous Delivery is the ability to get changes of all types -- including new features, configuration changes, bug fixes and experiments -- into <strong>production</strong>, or into the hands of users, safely and quickly in a sustainable way." <a title="[4:52] into" href="#[3]">[3]</a>

GoCD achieves CD with an <strong>automated pipeline of continuous testing and acceptance</strong> of small increments of changes to code always in a deployable state.

It's competitors include <a target="_blank" href="https://codefresh.io/">CodeFresh</a>,
<a target="_blank" href="https://jenkins-x.io/">Jenkins X</a>.


## Advantages & Value Proposition

GoCD provides visibility (traceability) over the end-to-end workflow from version control to production, even by teams of thousands of developers making changes through a complex pipelines on a daily basis.

## Automate out manual approvals

GoCD implements the vision of a pipeline to production as low-risk, predictable, routine, performed on demand. This is achieved by eliminating delays during "code freezes" for integration, testing, and hardening phases that traditionally followed “dev complete”. 

![gocd-pipeline-diagram-672x431](https://user-images.githubusercontent.com/300046/62833512-31e93d80-bbfd-11e9-95b9-1abb57abd5cb.jpg)
<p align="right"><a title="[12:54]" href="#[1]">[1]</a></p>

PROTIP: Wisdom from Thoughtworkers is that feature and long-lived branches are an anti-patterns.
Commit into master. They recommend that every commit should trigger a build.
And broken builds should be fixed immediately.
That is also the recommendation from Security experts, who say always "be ready for another Heartbleed vulnerability" which required rebuild of the core operating system. Technical debt block the quick action needed to remediate before hackers take advantage of vulnerabilities.


## Internal architecture

Unlike Jenkins, which has pipelines as tasks within each job,
GoCD's primary organization are <strong>pipelines</strong>. 

![gocd-main-menu-607x67](https://user-images.githubusercontent.com/300046/62833794-a45c1c80-bc01-11e9-8202-08eda331ee1f.png)

* <strong>Pipelines</strong> (can be grouped and given role-based permissions)
   * Sequential <strong>Stages</strong> running several <strong>Jobs</strong> (in parallel). If a particular stage fails, the whole pipeline job fails.

GoCD's <strong>Value Stream Maps</strong> track changes from commit to deploy and delivery:
<p align="right"><a target="_blank" href="https://user-images.githubusercontent.com/300046/62834026-2b11f900-bc04-11e9-8ce8-721338c24ee9.jpg"><img alt="gocd-map-2014-1920x1080.jpg" src="https://user-images.githubusercontent.com/300046/62834026-2b11f900-bc04-11e9-8ce8-721338c24ee9.jpg"></a><a title="[12:54]" href="#[1]">[1]</a> <a target="_blank" href="https://docs.gocd.org/current/navigation/value_stream_map.html">https://docs.gocd.org/current/navigation/value_stream_map.html</a></p>

PROTIP: You'll need to ask your Network Admin. to open up default port 8153 to serve UI/API and 8154 to control GoCD Agents.

<strong>Tasks</strong> (commands invoking shell scripts working on target servers)
   * <strong>Environments</strong> (Build, QA, Staging, Prod, etc.)
      * <strong>Agents</strong> contact (elastic) servers where work is done
         * <strong>Resources</strong> (tags about capabilities of each agent)

## Plugins

GoCD's proposition is (similar to GitLab) -- providing the most <strong>common CD scenarios out of the box</strong> - while Jenkins aims for general-purpose automation by extensibility with 3rd party plugins. That's how GoCD avoids the issue of plugins that can be  missing features, obsolete, or does not work well with others.

GoCD has a handful of extension points that are interoperable with each other: 

* SCM (Source Control Management) = Material Types (Git, Subversion, Mercurial, Perforce, TFS, Pipeline, Package) [32:42]
* tasks (Ant, NAnt, Rake)
* notifications, 
* authentication and authorization, 
* configuration, 
* elastic agents (for parallel execution at scale)
<br /><br />
