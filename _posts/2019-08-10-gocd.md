This article are my notes about GoCD, described at website <a target="_blank" href="https://www.gocd.org/">gocd.org</a> (previously at https://go.cd).

My contribution is a logical sequence of content for a deep yet concise presentation.

With "Go" in the name one would think that it's written in the <a target="_blank" href="https://wilsonmar.github.io/golang/">Go language</a>.
But GoCD is actually built using Java and JRuby on Rails. It was re-branded in 2010 before Google released the Go language. 

GoCD's first released was in 2014 as open-source at <a target="_blank" href="https://github.com/gocd/gocd">https://github.com/gocd/gocd</a>. <a target="_blank" href="https://www.gocd.org/releases/#14-1-0">GoCD's releases</a> are <a target="_blank" href="https://semver.org/">sematically</a> tagged beginning with a year (19 for 2019). 

Beginning from 20010, Jez Humble worked alongside a team in Beijing to create the product which later became GoCD.
They work at <a target="_blank" href="https://www.thoughtworks.com/">ThoughtWorks</a>, which makes money by providing <a target="_blank" href="https://www.gocd.org/plugins/">commercial (paid) plugins</a>, but primarily from consulting services. The company has a <a target="_blank" href="https://www.glassdoor.com/Reviews/ThoughtWorks-Reviews-E38334.htm">90% employee referral rating on Glassdoor.com</a>. 
Martin Fowler, its chief scientist since 2000 <a href="#[4]">[4]</a> (along with Jim Highsmith and other software visionaries) authored the <a target="_blank" href="https://agilemanifesto.org/">Agile Manifesto</a> in 2001.
In 2010, Thoughtworkers Jez Humble and David Farley wrote their oft-quoted book <a target="_blank" href="https://www.amazon.com/Continuous-Delivery-Deployment-Automation-Addison-Wesley-ebook/dp/B003YMNVC0">Continuous Delivery</a>. Jez Humble also co-wrote with Gene Kim the industry-leading DevOps Handbook.

## Delivery to Production, not just Deploy to Test

The "CD" in GoCD is for "Continuous Delivery" (not just Deployment). As Humble states in his website <a target="_blank" href="https://continuousdelivery.com/">ContinuousDelivery.com</a>:

> "Continuous Delivery is the ability to get changes of all types -- including new features, configuration changes, bug fixes and experiments -- into <strong>production</strong>, or into the hands of users, safely and quickly in a sustainable way." <a title="[4:52] into" href="#[3]">[3]</a>

GoCD achieves CD with an <strong>automated pipeline of continuous testing and acceptance</strong> of small increments of changes to code always in a deployable state (even by teams of thousands of developers making changes on a daily basis).

## Advantages & Value Proposition

Unlike Jenkins, which has pipelines as tasks within each job,
GoCD's primary organization are <strong>pipelines</strong>. GoCD's <strong>Value Stream Maps</strong> track changes from commit to deploy and delivery:
<p align="right"><a target="_blank" href="https://user-images.githubusercontent.com/300046/62834026-2b11f900-bc04-11e9-8ce8-721338c24ee9.jpg"><img alt="gocd-map-2014-1920x1080.jpg" src="https://user-images.githubusercontent.com/300046/62834026-2b11f900-bc04-11e9-8ce8-721338c24ee9.jpg"></a><a title="[12:54]" href="#[1]">[1]</a> <a target="_blank" href="https://docs.gocd.org/current/navigation/value_stream_map.html">https://docs.gocd.org/current/navigation/value_stream_map.html</a></p>

GoCD's provides visibility (traceability) over the end-to-end workflow from version control to production. 

GoCD works with both source programming code and infrastructure as code (configurations  leveraging Terraform, Ansible, Chef, Puppet, etc.)


## Internal architecture

![gocd-main-menu-607x67](https://user-images.githubusercontent.com/300046/62833794-a45c1c80-bc01-11e9-8202-08eda331ee1f.png)

* Pipelines (can be grouped and given role-based permissions)
   * Sequential Stages with Jobs running in parallel
      * Tasks (commands invoking shell scripts working on target servers)
   * Environments
      * Agents contact (elastic) servers
         * Resources (tags about capabilities of each agent)

## Automate out manual approvals

GoCD takes code through a pipeline to production as low-risk, predictable, routine affairs performed on demand. This is achieved by eliminating delays during "code freezes" for integration, testing, and hardening phases that traditionally followed “dev complete”.

## Plugins

GoCD's proposition is (similar to GitLab) -- providing the most <strong>common CD scenarios out of the box</strong> - while Jenkins aims for general-purpose automation by extensibility with 3rd party plugins. That's how GoCD avoids the issue of plugins that can be  missing features, obsolete, or does not work well with others.

GoCD has a handful of extension points that are interoperable with each other: 

* SCM (Source Control Management) = Material Types (Git, Subversion, Mercurial, Perforce, TFS, Pipeline, Package) [32:42]
* tasks (Ant, NAnt, Rake)
* notifications, 
* authentication and authorization, 
* configuration, 
* elastic agents (for parallel execution at scale)
