Written in the <a target="_blank" href="https://wilsonmar.github.io/golang/">Go language</a>, the OPA (Open Policy Agent) can be added several ways to add policy decision making. It was started in 2016 at <a target="_blank" href="https://www.styra.com/">Styra.com</a> (by @sometorin).

   <ul>"Declarative Authorization to Secure Kubernetes - Compliance guardrails so you can move your security from tribal knowledge to policy-as-code"
   </ul>

OPA's initial use case was for Kubernetes Orchestration Admission Control.

   <a target="_blank" href="https://blog.openpolicyagent.org/opas-full-stack-policy-language-caeaadb1e077"><img alt="opa-all-728x424" width="728" height="424" src="https://user-images.githubusercontent.com/300046/66733093-a3bb4e80-ee1b-11e9-849e-02a3002c94c3.png"></a>

Examples of other decisions OPA enables: [3:13:48]

   * Can user X do operation Y on resource Z?
   * Which annotations must be added to new Deployments?
   * Which users can SSH into production machines?
   * What invariants does workload W violate?
   * Which records should Bob be allowed to see?
   <br /><br />

OPA is called a <strong>general purpose</strong> policy engine because it
enables the answering of such policy questions above as a separate concern from enforcement.

OPA "policy enables" micro-services as a sidecar in <a target="_blank" href="https://wilsonmar.github.io/service-mesh">Service Mesh/Istio</a> for role-based fine-grained access control (<a target="_blank" href="https://www.youtube.com/watch?v=ctr2bVmzGpk">VIDEO Jun 25, 2019</a>).

   <a target="_blank" href="https://www.youtube.com/watch?v=3Ea9okBUY5Y"><img width="1191" alt="opa-usage-2382x966" src="https://user-images.githubusercontent.com/300046/66733321-64d9c880-ee1c-11e9-8332-578b8d1a304f.png"></a>

   OPA can be initiated as a host-level daemon via SSH to ensure that container executions are performed according to rules.

OPA maintains both policies and data <strong>in memory</strong> (for fast access).
So it operates as a host-local "cache" for policy decisions.

Enforcement Points are places where constraints can be enforced. Examples are Git hooks and Kubernetes admission controllers and audit systems. 

Target is an abstract concept. It represents a coherent set of objects sharing a common identification and/or selection scheme, generic purpose, and can be analyzed in the same validation context. 


Previous rules engines such as <a target="_blank" href="https://en.wikipedia.org/wiki/Drools">Drools</a> were designed with a "backward chaining inference", which was too strange and complicated. The rules were static logic.

## Rego rule declarations

But OPA's rules are dynamic over time and defined using a <strong>declarative syntax</strong> rather than a programmatic if-then-else logic referencing object classes, methods, and binary trees.

OPA declares Policy definitions in "Rego" text format, so they can be stored in GitHub.

OPA can respond with not just Boolean yes/no but also collections of values such as  numbers (e.g. rate-limits), strings (e.g. hostnames), arrays (e.g. servers), or dictionaries (microservice route-mappings). For more examples, see the <a target="_blank" href="http://www.openpolicyagent.org/docs/get-started.html">Open Policy Agent tutorials</a>.



It’s the policy author that knows what the data means in the real world and writes logic to make a policy decision.
